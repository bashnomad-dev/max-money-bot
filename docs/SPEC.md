# SPEC — max-money-bot (ТЗ v2.1 под Евгения, российский стек)

Дата: 2026-06-02
Статус: финальное ТЗ для реализации MVP под конкретного клиента.

> **Кто клиент.** Евгений (никнейм «Евгений Йога»), владелец строительного рынка с двумя точками **«Магазин Зинино»** и **«Магазин Кармалы»**. Работает один. Ассортимент — ~4893 SKU (пиломатериалы, цемент, метизы, отделка). Полный intake — [intake/evgeny/](./intake/evgeny/README.md).
>
> **Что изменилось относительно v2.0.** Стек переведён на российский (GigaChat + GigaAM + maxapi). Домен зафиксирован под Евгения. Multi-tenant убран (single-tenant навсегда). Порог крупной суммы поднят до 150k (B2B-отгрузки). Категории расходов сокращены до реальных. Единицы измерения — только 10 реальных из прайса. Импорт прайса обязателен в setup. Tools упрощены под GigaChat function calling. Историческое v2.0 ТЗ — в `docs/archive/`.

---

## 1. Vision & Problem

### 1.1 Кто пользователь
**Евгений**, владелец двух точек строительного рынка («Магазин Зинино», «Магазин Кармалы»). Один работает. Бухгалтер есть, но «не на розницу». Учёт **в голове**: «У меня всё вылетает из башки. Так в голове плюс минус. Чуйка».

### 1.2 Боль
Прямые цитаты:
- «Я ничего не записываю».
- «Я просто этот доходов ни уходов не успеваю».
- «Пытался вести. Но нужно вносить данные, а я не успеваю. Забываю».

К концу месяца невозможно понять, какая точка в плюсе, что лежит мёртвым грузом (3-4 млн ₽ заморожено), куда уходят деньги. Цена ошибки — оборачиваемость и собственная усталость.

### 1.3 Решение
Голосовой бот в MAX. Евгений надиктовывает «как есть» по ходу дня, бот сам разбирает в три листа Google-таблицы. В 21:00 МСК — текстовый итог. По запросу голосом — отчёт за период и остатки.

### 1.4 Метрика успеха пилота
Через 2 недели использования Евгений может в любой момент назвать:
- Сегодняшние выручку, расход, итог.
- Топ-3 точки по выручке за месяц.
- Остаток по топ-20 товарам (категории A из ABC-анализа).

И тратит на это не больше 10 секунд (один голосовой запрос).

### 1.5 То, что бот НЕ решает
Главная боль Евгения по его словам — **бумаги** (договора, акты сверки, счета, отчётности). Это **другой проект**, не этот бот. Чётко проговариваем при старте.

## 2. Канал и пользователи

**Канал:** только MAX. Не Telegram, не WhatsApp.

**Пользователь:** один — Евгений. `ALLOWED_USER_IDS` = его MAX user_id. Все остальные — отказ (флаг `SILENT_REJECT` для молчания).

**Юрлицо для регистрации бота в MAX:** одно из 3 ООО Евгения. У пользователя 3 организации — закрывает квартал по ним. На этапе разработки (Фаза B по [intake/evgeny/README.md](./intake/evgeny/README.md)) — тестовый бот в личном режиме или на твоё/Дмитрия юрлицо.

**Опасные команды** (`/undo`, `/edit last`) — защищены `OPS_PIN` если он задан.

## 3. Принципы работы

1. Только MAX. Long-polling в MVP (без публичного HTTPS).
2. Ввод — голос. Текст тоже принимается (для правок и команд).
3. Все учётные операции — в Google Sheets. SQLite — только техслой.
4. Распознавание речи — **GigaAM** локально (бесплатно). Fallback — Whisper API при недоступности.
5. Парсинг текста → структуру — **GigaChat function calling**. Fallback — повтор на GigaChat-Max при низком confidence.
6. **Транзакция связанных записей** через общий `tx_id` (продажа = деньги + товары + остатки одним пакетом).
7. **Гибридный UX подтверждения** (см. §9): high confidence → запись + ✅-реакция; иначе карточка / уточнение.
8. **Крупная сумма > 150 000 ₽** → всегда карточка (B2B-отгрузки у Евгения часты, нужен предохранитель).
9. Бот не пишет молча сомнительные операции.
10. **Append-only**: клиент может добавлять любые свои колонки справа от ботовских — бот их игнорирует.
11. Канонизация SKU и точек **обязательна** — иначе остатки разъезжаются и отчёты врут.
12. Семантическая дедупликация в окне 5 минут (защита от повторной диктовки).
13. Escape-команда «отмена» / «забей» / `/cancel` сбрасывает любой активный диалог.

## 5. Сценарии использования

Полные кейсы — [scenarios.md](./scenarios.md). Тут крупно.

### S1. Продажа (high confidence)
Голос: «Продал 30 мешков цемента Стерлитамак Хайдел за 18 тысяч наличными на Зинино»
→ деньги (приход 18000, продажа, наличные, Зинино) + товары (продажа 30 мешок, Зинино) + остатки (Зинино: 30 → 0 мешков).
Бот ставит ✅-реакцию на сообщение пользователя.

### S2. Закупка
Голос: «Получил от Петровича 100 мешков штукатурки за 25 тысяч безналом на Кармалы»
→ деньги (расход 25000, закупка) + товары (поступление 100 мешок, Кармалы) + остатки + пересчёт СВ-цены.

### S3. B2B-отгрузка крупному клиенту
Голос: «Иванов забрал 50 досок 50×150×6000 за 75 тысяч счётом, Зинино»
→ сумма 75k < 150k порога → запись сразу, ✅-реакция.
Если бы 300k → карточка с подтверждением.

### S4. Возврат от покупателя
Голос: «Возврат от Иванова: вернули 2 листа гипсокартона, отдал 800 рублей наличными, Зинино»
→ деньги (расход 800, возврат покупателю) + товары (поступление 2 лист, Зинино) + остатки +2.

### S5. Списание
Голос: «Списал 3 мешка штукатурки на Зинино, бой»
→ только товары (списание -3, комментарий «бой») + остатки -3.

### S6. Расход без товара
Голос: «Заплатил аренду 80 тысяч на счёт за Зинино»
→ только деньги (расход, аренда, счёт, Зинино).

### S7. Перемещение между точками
Голос: «Перевёз 20 листов ГКЛ из Зинино в Кармалы»
→ товары (две связанные строки: -20 Зинино, +20 Кармалы) + остатки в обеих точках.

### S8. Запрос остатков голосом
«Сколько цемента Стерлитамак в Зинино?» → читаем лист «Остатки» → «Зинино: 47 мешков цемента Стерлитамак Хайдел 25 кг».

### S9. Дневной автоотчёт (21:00 МСК)
```
Финансы за 02.06.2026:
– Приход: 145 000 ₽ (12 операций)
– Расход: 78 500 ₽ (5 операций)
– Итог: +66 500 ₽

По точкам:
  Зинино: +42 000 ₽
  Кармалы: +24 500 ₽

Топ-3 товара по выручке:
  1. Доска Хв 50×150×6000 — 45 000 ₽ (9 шт)
  2. Цемент Стерлитамак Хайдел 25 кг — 28 000 ₽ (87 мешков)
  3. Брус Хв 100×200×6000 — 22 000 ₽ (4 шт)
```

### S10. Голосовой сводный отчёт за период
«Отчёт за месяц по выручке» → диалог уточнения → отчёт текстом за выбранный период.

### S11. `/undo`, `/edit last`, `/today`, `/stock`, `/inventory`
См. подробности в [scenarios.md](./scenarios.md).

### S12. Канонизация нового товара
Голос с товаром, которого нет в прайсе → бот: «Не нашёл «доску дюймовку» в каталоге. Это новый товар или вариант существующего?» (с предложенными по similarity).

## 6. Структура Google-таблицы

Полная схема — [data-model.md](./data-model.md). Кратко:

### 6.1 Обязательные листы (3)
- **Движение денег** (10 колонок).
- **Движение товаров** (12 колонок).
- **Остатки** (6 колонок) — автообновляется ботом.

### 6.2 Справочные листы (3)
- **Товары** — справочник 4893 SKU, импортируется один раз из прайса Евгения.
- **Точки** — 2 строки: «Магазин Зинино», «Магазин Кармалы».
- **Категории расходов** — 9 редактируемых категорий.

### 6.3 Опциональный лист
- **Лог обработки** — если `ENABLE_PROCESSING_LOG_SHEET=true`.

### 6.4 Setup при первом `/link`
1. Проверка прав service account.
2. Создание всех листов с заголовками.
3. Импорт **Точек** из ENV (`Магазин Зинино`, `Магазин Кармалы`).
4. Импорт **Категорий** из дефолтного списка (§10.3).
5. Импорт **Товаров** из `data/products-import.json` (нормализованный прайс из intake).
6. Лист «Остатки» создаётся пустым, заполняется по мере первых операций.

## 7. Канонизация

### 7.1 Точки (обязательная)
Каталог в листе «Точки» (2 строки). Голосовое «Зинино», «магазин на Зинино», «зинино» → канон «Магазин Зинино» через нормализацию (lowercase, без префиксов «магазин»).

### 7.2 Товары (обязательная, импорт обязателен)
4893 канонических SKU из прайса. При произнесении товара бот ищет в листе «Товары» через **fuzzy matching** (`rapidfuzz`):
- similarity ≥ 0.9 → автоподстановка канонического имени.
- 0.7–0.9 → карточка с предложением 1-3 вариантов.
- < 0.7 → карточка «новый товар? предложи единицу измерения и цену».

Кеш в SQLite `products_cache`, синхронизация с листом раз в час.

### 7.3 Контрагенты (в MVP — НЕ канонизируем)
Контрагенты в свободной форме. Канонизация — v2 (пока имена «Петрович», «Иванов», «Леруа Мерлен» хранятся как есть). Это упрощает MVP и снимает риск ложного склеивания.

## 8. Семантическая дедупликация

Защищает от повторной диктовки (Евгений может не услышать ответ в шуме рынка и надиктовать заново).

`semantic_hash = sha256(тип_операции + сумма_округлённая_до_сотен + товар + точка)` в окне 5 минут.

Совпадение → карточка «Уже была такая операция в 14:32. Повтор или новая?» с двумя кнопками.

## 9. Гибридная модель подтверждения

### 9.1 Порядок проверок
```
1. Новый товар / новая точка не из каталога → карточка канонизации
2. Сумма > LARGE_AMOUNT_THRESHOLD_RUB (дефолт 150 000) → карточка
3. Семантический хэш в dedup_window → карточка «повтор?»
4. critical_confidence = min(text, amount, quantity):
     ≥ 0.85 → запись + ✅-реакция (без текстового сообщения)
     0.5–0.85 → карточка с подтверждением до записи
     < 0.5 → request_clarification (текст вопроса, ничего не пишем)
```

### 9.2 Подтверждение через реакцию ✅
В MAX (по аналогии с Telegram) бот может ставить эмодзи-реакции. Используем ✅ как подтверждение «записал, всё ок». Это в **разы тише** чем «Записал продажу 18000 ₽...» текстом на каждую операцию. Если MAX не поддерживает реакции в Bot API — fallback на короткое текстовое «✅ записал».

### 9.3 Тексты уточнений
| Случай | Текст |
|--------|------|
| Не понял команду | «Не понял операцию. Это продажа, закупка, расход, возврат или что?» |
| Нет суммы для финопера | «Какую сумму записать?» |
| Нет товара для товарной | «Что именно записать?» |
| Нет количества | «Какое количество?» |
| Whisper мусор/тишина | «Не разобрал. Попробуй ближе к микрофону.» |
| Точка не указана и default нет | «На какую точку: Зинино или Кармалы?» |
| Чат не привязан | «Сначала /link <ID> и расшарь таблицу на: \<service email\>» |
| Чужой user_id | (молчание при SILENT_REJECT) или «Доступа нет» |

## 10. Лист «Движение денег»

### 10.1 Колонки (10)
| # | Колонка | Тип |
|---|---------|-----|
| 1 | Дата | ДД.ММ.ГГГГ |
| 2 | Время | ЧЧ:ММ |
| 3 | Тип операции | enum (§10.2) |
| 4 | Сумма (₽) | целое число |
| 5 | Описание | строка |
| 6 | Категория | enum (§10.3) — только для расходов; для остальных пусто |
| 7 | Контрагент | строка / «не указано» |
| 8 | Точка | «Магазин Зинино» / «Магазин Кармалы» |
| 9 | Способ оплаты | наличные / карта / счёт / не указано |
| 10 | tx_id | служебный (связь с «Движение товаров») |

### 10.2 Типы операций денег (8)
- **продажа** — приход от покупателя за товар
- **закупка** — расход поставщику за товар
- **расход** — без товара (аренда, зарплата, налоги...)
- **прочий приход** — без товара (бонус, штраф контрагенту в нашу пользу, страховка)
- **возврат покупателю** — расход (вернули деньги покупателю)
- **возврат поставщика** — приход (поставщик вернул деньги)
- **внесение** — пополнение кассы из своих денег
- **изъятие** — забор владельцем из кассы на личное

### 10.3 Категории расходов (9)
1. закупка товара (для типа «закупка» автоматом)
2. аренда помещения
3. зарплата
4. коммунальные / связь
5. реклама / маркетинг
6. транспорт / доставка
7. налоги / банк / эквайринг
8. оборудование / ремонт
9. прочее

Список редактируется в листе «Категории». Бот при запуске читает актуальный.

## 11. Лист «Движение товаров»

### 11.1 Колонки (12)
| # | Колонка | Тип |
|---|---------|-----|
| 1 | Дата | ДД.ММ.ГГГГ |
| 2 | Время | ЧЧ:ММ |
| 3 | Тип операции | enum (§11.2) |
| 4 | Точка | канон из «Точек» |
| 5 | Точка-источник | для перемещений (откуда), иначе пусто |
| 6 | Товар | канон из «Товары» |
| 7 | Количество | число (может быть дробным) |
| 8 | Единица | канон (см. §11.3) |
| 9 | Цена за ед. (₽) | для продаж — СВ-цена закупки на момент; для закупок — фактическая |
| 10 | Контрагент | строка / «не указано» |
| 11 | Комментарий | строка |
| 12 | tx_id | связь с «Движение денег» |

### 11.2 Типы операций товаров (7)
- **поступление** — от поставщика на точку
- **продажа** — со склада/точки покупателю
- **списание** — брак, недостача
- **возврат покупателя** — товар вернулся на точку
- **возврат поставщику** — товар уехал поставщику
- **перемещение** — между точками (две связанные строки)
- **инвентаризация** — корректировка по результатам сверки факта с расчётом

### 11.3 Единицы измерения (10 реальных, из прайса Евгения)
По частоте в прайсе: `шт.` (7160), `м2` (732), `м3` (550), `м.п.` (421), `рул` (280), `уп.` (255), `кг` (246), `меш.` (82), `л.` (46), `м` (14).

Канонизация в `src/llm/canonicalize.py`: «штук» → `шт.`, «мешков» → `меш.`, «квадратных метров» → `м2`. Незнакомая единица → пишется как есть + логируется в SQLite `unknown_units`.

## 12. Лист «Остатки»

### 12.1 Колонки (6)
| Колонка | Тип |
|---------|-----|
| Товар | канон из «Товары» |
| Точка | канон из «Точек» |
| Количество | число |
| Единица | канон |
| Средневзвешенная цена закупки (₽) | для расчёта прибыли |
| Обновлено | ДД.ММ.ГГГГ ЧЧ:ММ |

### 12.2 Обновление
- При каждой операции из «Движение товаров» — пересчёт строки `(товар, точка)`.
- При перемещении — две строки (источник -, приёмник +).
- При инвентаризации — установка нового значения, разница пишется в «Движение товаров» как корректировка.
- СВ-цена обновляется только при поступлении: `новая_свц = (старое_кол × старая_свц + новое_кол × новая_цена) / (старое_кол + новое_кол)`.

### 12.3 Защита от ручных правок
Лист помечен как «system» в первой ячейке `A1` (фиксированный заголовок). При обнаружении изменения вне ботовских операций — бот фиксирует предупреждение в чат: «Лист Остатки правлен вручную. Запусти `/repair stock` для пересчёта».

`/repair stock` — пересчитывает все строки из «Движения товаров» с нуля.

### 12.4 Отрицательные остатки
При расчёте остаток уйдёт в минус → перед записью карточка: «Внимание: остаток ГКЛ 12,5 в Зинино уйдёт в −5 листов. Возможно пропущено поступление. Записать всё равно?»

## 13. Отчёты

### 13.1 `/today` — промежуточный
```
На сейчас (15:42, 02.06.2026):
– Приход: 78 000 ₽ (4 операции)
– Расход: 25 000 ₽ (1 операция)
– Итог: +53 000 ₽

По точкам: Зинино +35k, Кармалы +18k.
```

### 13.2 Ежедневный автоотчёт (21:00 МСК)
Формат — см. S9. Ретрай 5 раз при сбое Sheets, накопительный отчёт на следующий день при провале.

### 13.3 Сводный отчёт за период
Триггер: `/report` или «отчёт за месяц». Уточнение периода: «текущий или конкретный?».

Формат:
```
Финансовый отчёт за июнь 2026:
– Приход: 1 240 000 ₽ (165 операций)
– Расход: 890 000 ₽ (42 операции)
– Итог: +350 000 ₽

По точкам:
  Магазин Зинино: +210 000 ₽
  Магазин Кармалы: +140 000 ₽

Топ-3 товара по выручке:
  1. ...
  2. ...
  3. ...
```

### 13.4 Метрика топа
По дефолту — **по выручке**. Альтернативы по голосовой команде: «по прибыли», «по количеству». Топ-5 точек/товаров.

### 13.5 `/stock`
```
Остатки на 02.06.2026 15:42:

Цемент Стерлитамак Хайдел 25 кг:
  Зинино: 47 мешков
  Кармалы: 23 мешков

Доска Хв 50×150×6000:
  Зинино: 12 шт
  Кармалы: 28 шт
  ...
```

С параметром `/stock цемент` — только товары по фильтру. `/stock цемент Зинино` — товары на конкретной точке.

## 14. Архитектура

### 14.1 Источник правды
Sheets — учётные данные. SQLite — техсостояние (idempotency, dedup, dialog_state, operations_log, pending_writes, products_cache, locations_cache, unknown_units, missed_reports).

### 14.2 Стек
| Слой | Технология | Заметки |
|------|------------|---------|
| MAX Bot API | `maxapi` (Python) | Готовая библиотека, как у фрилансера. Long-polling в MVP. |
| STT | **GigaAM** (локально) | Бесплатно, российская модель Сбера. `gigaam` PyPI. Требует `ffmpeg` + ~1 ГБ модели. |
| LLM | **GigaChat** (function calling) | `gigachat` PyPI. Модель `GigaChat-Max`, fallback `GigaChat-Pro`. |
| Sheets | `gspread` + service account | Стандарт. |
| SQLite | `sqlite3` (стд библиотека) | + `aiosqlite` опц. для async. |
| HTTP | `httpx.AsyncClient` | Для побочных API. |
| Планировщик | `apscheduler` | Дневной отчёт. |
| Fuzzy matching | `rapidfuzz` | Канонизация SKU. |

### 14.3 LLM-абстракция
В `src/llm/` интерфейс `LLMParser` с двумя реализациями: `GigaChatParser` (основная) и `ClaudeParser` (резерв). Переключение через `LLM_BACKEND=gigachat|claude` в env. Это гарантирует, что если GigaChat не справится на каком-то edge case — переключаемся за 5 минут.

### 14.4 Модули
```
src/
  main.py            — точка входа
  bot/               — maxapi-клиент, роутер
  stt/               — GigaAM (основное) + Whisper (fallback)
  llm/               — интерфейс LLMParser + GigaChat + Claude
  sheets/            — gspread, инициализация, маппинг ops → строки
  stock/             — пересчёт остатков, СВ-цена, /repair
  domain/            — pydantic-модели
  reports/           — расчёт отчётов
  scheduler/         — apscheduler для дневного отчёта
  storage/           — SQLite слой
  dialog/            — stateful-диалоги (clarification, canonicalization, undo confirm)
  canonicalize/      — fuzzy matching SKU/точек/единиц
  config/            — env, whitelist
```

### 14.5 Поток данных
```
MAX (voice) → GigaAM (text) → GigaChat (ParsedCommand)
                                        ↓
                            ┌────────────┼────────────┐
                            ↓            ↓            ↓
                       запись сразу   карточка    clarification
                            ↓            ↓            ↓
                       Sheets append  ждём ✅     dialog_state SQLite
                            ↓
                       SQLite operations_log (для /undo)
                            ↓
                       ✅-реакция в MAX
```

### 14.6 Транзакционность Sheets
Sheets не транзакционна между листами. Стратегия:
1. Сначала пишем в **Движение товаров** (если есть товарная часть).
2. Потом в **Движение денег** (если есть денежная часть).
3. Потом обновляем **Остатки** (если есть товарная часть).
4. При сбое на любом шаге — компенсация (удалить только что записанное) + запись в `pending_writes` для повтора.
5. `/undo` ищет все строки по `tx_id` и удаляет одной серией + пересчёт остатков.

## 15. AI-парсинг (GigaChat function calling)

Полное — [llm-parsing.md](./llm-parsing.md). Кратко:

### 15.1 Tools (8, упрощено относительно v2.0 для GigaChat)
1. `record_sale` — продажа товара (деньги + товар + остатки)
2. `record_purchase` — закупка товара (расход + поступление + остатки + СВ-цена)
3. `record_return` — возврат (тип в поле: from_customer / to_supplier)
4. `record_cashflow` — приход/расход без товара (аренда, зарплата, внесение, изъятие)
5. `record_writeoff_or_movement` — списание или перемещение между точками
6. `record_inventory` — корректировка остатка по факту
7. `query_or_report` — вопрос по остаткам или отчёт за период
8. `request_clarification` — нет критичных полей или непонятно

### 15.2 Системный промпт
Адаптирован под GigaChat (более директивный, короткий, меньше абстракций). См. [llm-parsing.md](./llm-parsing.md) §4.

## 16. Нефункциональные требования

### 16.1 Производительность
Целевое: голос отправлен → реакция в чате **< 6 сек** (GigaAM локально — без сетевой задержки на STT).

### 16.2 Лимиты
- Голосовое: ≤ 120 сек (GigaAM пережёвывает дольше Whisper).
- Sheets API: 60 req/min — несущественно для одного пользователя.
- GigaChat — лимиты тарифа Сбера.

### 16.3 Безопасность
- Whitelist `ALLOWED_USER_IDS`.
- `OPS_PIN` для опасных команд.
- Секреты только в `.env` (600), `secrets/` (600).
- `gigachat` использует self-signed сертификаты Сбера → `verify_ssl=false` допустимо.
- Логи без секретов и токенов.

### 16.4 Надёжность
- Падение GigaChat → fallback на ClaudeParser (если `LLM_BACKEND_FALLBACK=claude` и есть `ANTHROPIC_API_KEY`); иначе сообщение пользователю.
- Падение GigaAM → fallback на Whisper API.
- Падение Sheets → очередь `pending_writes`, ретрай 60 сек.
- Падение бота → systemd рестарт, SQLite сохраняет состояние.

### 16.5 Бюджет
Оценка для Евгения (50-100 операций/день, преимущественно через GigaAM):
- GigaAM — 0 ₽ (локально).
- GigaChat-Max — ~600-1500 ₽/мес (зависит от тарифа Сбера, тарификация по токенам).
- VPS — 500-1500 ₽/мес.
- Google Sheets, MAX — 0 ₽.
- **Итого: ~1000-3000 ₽/мес.** Бюджет фрилансера (1500-2000 ₽/мес) реалистичен.

`MONTHLY_API_BUDGET_RUB` в env — при превышении бот предупреждает владельца.

## 20. Глоссарий

| Термин | Значение |
|--------|----------|
| Точка | Магазин Зинино или Магазин Кармалы |
| SKU | Уникальный товар в каталоге (4893 позиций) |
| Канон | Каноническое имя из справочника (Точки / Товары / Единицы) |
| tx_id | Идентификатор транзакции, связывающий записи в Деньгах, Товарах, Остатках |
| СВ-цена | Средневзвешенная цена закупки товара на точке |
| Операция | Атомарное событие учёта: одна продажа, одно поступление, один расход |
| Дедуп-окно | 5 минут защиты от повторной диктовки той же операции |
| ✅-реакция | Эмодзи-реакция бота на сообщение пользователя — тихое подтверждение |
