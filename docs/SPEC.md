# SPEC — max-money-bot (итоговое ТЗ v2.0)

Дата: 2026-05-31
Статус: финальное ТЗ под домен «розничный магазин стройматериалов».
Source of truth — этот документ.

> **Историческая справка.** Версия v1.0 была построена на ошибочном брифе с примерами из домена «прораб/ремонтник» (объекты Петрова, ремонт ванной). Реальный домен — розничный магазин стройматериалов с несколькими точками/складами. v1.0 архивирована в `docs/archive/`.

## 1. Vision & Problem

### 1.1 Пользователь
Владелец розничного магазина стройматериалов с несколькими точками продаж и/или складами. Делает сам: крупные закупки у поставщиков, контроль кассы, разбор возвратов, инвентаризации. Продавцы за прилавком работают своими инструментами (касса, 1С, тетрадка) — данные оттуда в этот учёт не идут.

### 1.2 Боль
- Sheets с учётом ведётся руками — открыть с телефона на ходу неудобно, постоянно копится бэклог операций.
- Расчётные остатки расходятся с фактом: какие-то закупки записал, какие-то нет, когда что списал — не помнит.
- К концу месяца нельзя ответить «какая точка приносит, какая в минус», «какой товар самый ходовой», «сколько висит у Петровича».

### 1.3 Решение
Голосовой бот в MAX. Владелец надиктовывает операцию — бот распознаёт, парсит, **одновременно** обновляет три листа (Движение денег, Движение товаров, Остатки) транзакционно через общий `tx_id`. Дневной автоотчёт в 21:00 + сводные по голосу + запрос остатков голосом в любой момент.

### 1.4 Метрика успеха MVP
Владелец в течение 2 недель ежедневно вносит ≥80% крупных операций (закупки, возвраты, расходы, инвентаризации) через бота без возврата к ручному заполнению. После месяца — расчётные остатки сходятся с фактом в пределах 5% по топ-10 товарам.

## 2. Канал и пользователи

### 2.1 Канал
Только MAX. Не Telegram, не WhatsApp, не VK, не SMS.

### 2.2 Пользователи MVP
- **Владелец** — единственный, в whitelist `ALLOWED_USER_IDS`.
- Продавцы, снабженцы, бухгалтер — **не пользуются** ботом (v2+: роли).

### 2.3 Доступ
- Whitelist по MAX `user_id`. Чужим — отказ или молчание (`SILENT_REJECT`).
- PIN `OPS_PIN` обязателен для опасных команд (`/undo`, `/edit`, `/inventory`, корректировка остатков). Если не задан — операции работают без PIN, но логируются.

### 2.4 Tenancy
Single-tenant: один бот = один магазин. Multi-tenant не закладываем — упрощает архитектуру в разы.

## 3. Принципы работы

1. **Бот работает только в MAX.** Основной ввод — голос, текст тоже принимается.
2. **Sheets — единственный источник правды для учёта.** SQLite — только технический слой (идемпотентность, состояние диалогов, audit-log для `/undo`, очередь pending_writes).
3. **Транзакционность.** Операции, затрагивающие деньги И товары (продажа, закупка, возвраты), записываются атомарно: либо обе записи + пересчёт остатков, либо ни одной. Связь через общий `tx_id`.
4. **Автоматическая связь деньги ↔ товары ↔ остатки.** При записи продажи/закупки бот сам обновляет все три листа. Раздельной записи денег и товаров для одной транзакции не предполагается.
5. **Остатки — расчётные, не вводятся напрямую.** Пользователь не правит лист «Остатки» руками — он перезаписывается ботом. Для корректировки факта — команда `/inventory`.
6. **Гибридный UX подтверждения** (см. §9):
   - high confidence → запись сразу + постфактум подтверждение,
   - medium → карточка до записи,
   - low / не хватает обязательных полей → уточняющий вопрос.
7. **Крупные суммы** (> `LARGE_AMOUNT_THRESHOLD`, дефолт 100 000 ₽ — у магазина частые крупные закупки) — **всегда карточка** перед записью.
8. **Новый товар или точка** — всегда карточка с подтверждением канона.
9. **Каждая успешная запись подтверждается** сообщением в MAX.
10. **Структура колонок в Sheets — фиксированная** (см. [data-model.md](./data-model.md)). Клиент может добавлять свои колонки **только справа** от ботовских (см. §21).
11. **Канонизация товаров и точек** через справочные листы (см. §7).
12. **Семантическая дедупликация** в окне 5 минут (см. §8).
13. **Escape-команда** «отмена» / «забей» работает в любом диалоге; `/cancel` тоже.

## 5. Сценарии использования

Подробные кейсы с примерами фраз — [scenarios.md](./scenarios.md). Здесь — крупно.

### S1. Розничная продажа
«Продал 10 листов ГКЛ за 5 тысяч, наличными» → Деньги (приход 5000 наличные) + Товары (продажа -10 листов ГКЛ) + Остатки (пересчёт). Связь через `tx_id`.

### S2. Оптовая продажа бригаде
«Бригаде Иванова отгрузил 50 мешков цемента за 30 тысяч на счёт» → Деньги (приход 30000 счёт, контрагент Иванов) + Товары (продажа -50 мешков цемента) + Остатки. Контрагент сохраняется.

### S3. Закупка от поставщика
«Получил от Петровича 100 мешков штукатурки за 25 тысяч, безналом» → Деньги (расход 25000 счёт, контрагент Петрович) + Товары (поступление +100 мешков штукатурки, цена за единицу 250 ₽) + Остатки (увеличение, обновление средневзвешенной цены).

### S4. Возврат от покупателя
«Возврат: вернули 2 листа ГКЛ, отдал тысячу наличными» → Деньги (расход 1000 наличные, категория «возврат покупателю») + Товары (возврат +2 листа на склад) + Остатки.

### S5. Возврат поставщику
«Вернул Петровичу 10 мешков штукатурки, получил 2500 на счёт» → Деньги (приход 2500 счёт, категория «возврат поставщика») + Товары (возврат -10 мешков со склада) + Остатки.

### S6. Списание (брак, недостача)
«Списал 3 мешка штукатурки, бой» → Только Товары (списание -3 мешка, комментарий «бой») + Остатки. Деньги не трогаются.

### S7. Расход без товара
«Заплатил за аренду 80 тысяч на счёт» → Только Деньги (расход 80000, категория «аренда помещения»). Товары и остатки — без изменений.

### S8. Внесение / изъятие из кассы
«Внёс в кассу 50 тысяч своих» → Деньги (приход 50000, категория «внесение»).
«Снял из кассы 20 тысяч на личные» → Деньги (расход 20000, категория «изъятие»).

### S9. Перемещение между складами
«Перевёз 20 листов ГКЛ со склада на магазин на Ленина» → Только Товары (две строки: -20 склад, +20 Ленина, `tx_id` общий) + Остатки. Деньги не трогаются.

### S10. Запрос остатков голосом
«Сколько ГКЛ на складе?» → бот читает Остатки, отвечает: «ГКЛ на складе: 47 листов. Везде: 62 листа (47 склад, 15 Ленина).»

### S11. Инвентаризация
`/inventory` или «Инвентаризация ГКЛ» → бот: «Расчётный остаток ГКЛ: 47 листов. Сколько по факту?» → User: «Сорок пять» → бот фиксирует корректировку (-2 листа, категория «инвентаризация»), пересчитывает Остатки.

### S12. Multi-ops (несколько операций в одной фразе)
«Сегодня продал: цемент 30 мешков за 18 тысяч, ГКЛ 10 листов за 5 тысяч, всё наличными» → 2 транзакции продажи, общий итог в подтверждении.

### S13. Сводный отчёт
«Отчёт за месяц по выручке» → диалог уточнения если нужно → текстовый отчёт: выручка / расходы / прибыль, по категориям, топ-точек, топ-товаров.

### S14. Крупная сумма → карточка
«Закупил у Петровича цемент на сто пятьдесят тысяч» → сумма > 100 000 ₽ → карточка с подтверждением до записи, даже при high confidence.

### S15. Новый товар → канонизация
«Продал 5 банок жидких гвоздей за 2 тысячи» (товара «жидкие гвозди» нет в справочнике) → бот: «Не нашёл «жидкие гвозди» в справочнике. Завести как новый товар? Единица — банка?» → ✅ → создаётся канон, записывается продажа.

### S16. Новая точка → канонизация
Аналогично S15 — для новой торговой точки.

### S17. Дедупликация
Та же продажа за 5 минут до этого → бот не пишет, спрашивает «Уже была такая в 14:30: продажа 10 листов ГКЛ за 5000 ₽. Повтор или новая?»

## 6. Структура Google-таблицы

См. [data-model.md](./data-model.md). Кратко:

### 6.1 Обязательные листы (создаются ботом при `/link`)
- **Движение денег** (10 колонок) — все денежные операции.
- **Движение товаров** (11 колонок) — все товарные операции.
- **Остатки** (6 колонок) — расчётные остатки, **автообновление ботом**, владелец руками не правит.

### 6.2 Справочные листы (создаются автоматически по мере появления данных)
- **Товары** — канонические имена + алиасы + дефолтная единица измерения.
- **Точки** — торговые точки и склады, канон + алиасы + тип.
- **Категории** — редактируемый список категорий расходов.

### 6.3 Опциональный технический лист
- **Лог обработки** — если `ENABLE_PROCESSING_LOG_SHEET=true`, дублирует часть SQLite в Sheets для удобства владельца.

### 6.4 Иерархия привязки таблицы
1. SQLite `chat_sheets[chat_id]` — приоритет.
2. Иначе `DEFAULT_SHEET_ID` из env.
3. Иначе — инструкция сделать `/link <id>`.

### 6.5 Инициализация
При первом `/link` бот:
1. Проверяет права service account на запись.
2. Создаёт обязательные листы со заголовками, если их нет.
3. Если листы есть, но колонки не совпадают — отказ.
4. Справочные и Лог — лениво, при первой записи.

## 7. Канонизация товаров и точек

### 7.1 Зачем
- Один и тот же товар пользователь произносит по-разному: «гипсокартон 12,5», «ГКЛ», «ГКЛ влагостойкий 12,5» — без канонизации остатки врут.
- То же с точками: «склад», «база», «склад на Зорге» — три разных строки в отчёте по точкам.

### 7.2 Поток (одинаковый для товаров и точек)
1. При первой встрече нового имени бот ищет похожие в кэше / справочном листе (fuzzy match, similarity > 0.8).
2. **Если нашлось похожее:** карточка «Это «ГКЛ 12,5» или новый товар «ГКЛ влагостойкий»? [✅ Та же] [➕ Новая]».
3. **Если ничего нет:** карточка «Новый товар «жидкие гвозди». Единица измерения — банка? [✅ Да] [✏️ Поправить]».
4. **После решения** канон или alias сохраняется в справочный лист.
5. **Все будущие операции** идут под каноном; alias автоматически распознаётся.

### 7.3 Команды управления справочниками
- `/products [фильтр]` — список товаров. С фильтром «ГКЛ» — все ГКЛ-варианты.
- `/locations` — список точек.
- Редактирование канонов и алиасов — **руками в Sheets**, бот подхватывает раз в час и при каждой записи новой строки.

## 8. Семантическая дедупликация

### 8.1 Зачем
Защита по `MAX message_id` спасает от webhook retry. Не спасает от: пользователь забыл и надиктовал ту же продажу через 10 минут; в шуме не услышал подтверждение, повторил.

### 8.2 Как
1. После парсинга, перед записью, бот считает `semantic_hash = sha256(op_type + товар + округлённое_количество + округлённая_сумма + контрагент)`.
2. Ищет в SQLite `dedup_window` (TTL = `DEDUP_WINDOW_MINUTES`, дефолт 5 мин) совпадающий ключ.
3. Если найден — карточка: «Уже была такая в 14:30: продажа 10 листов ГКЛ за 5 000 ₽. Повтор или новая?» с кнопками `[🔁 Повтор]` `[➕ Новая]`.
4. Ответ «новая» — записывается с новым timestamp; «повтор» — не записывается, фиксируется в Логе.

## 9. Гибридная модель подтверждения

### 9.1 Пороги (настраиваются env)
- `AUTO_WRITE_CONFIDENCE_THRESHOLD` (дефолт 0.85) — выше → запись сразу.
- `CLARIFICATION_THRESHOLD` (дефолт 0.5) — ниже → уточняющий вопрос.
- `LARGE_AMOUNT_THRESHOLD_RUB` (дефолт **100 000** — у магазина частые крупные закупки, выше чем у прораба) — выше → карточка независимо от confidence.

### 9.2 Принципы принятия решения
```
если op требует канонизации нового товара или новой точки:
    → карточка с канон-вопросом (всегда)
иначе если amount > LARGE_AMOUNT_THRESHOLD_RUB:
    → карточка с подтверждением
иначе если semantic_hash в dedup_window:
    → карточка «повтор или новая?»
иначе если critical_confidence ≥ AUTO_WRITE_CONFIDENCE_THRESHOLD:
    → запись сразу + постфактум подтверждение
иначе если critical_confidence ≥ CLARIFICATION_THRESHOLD:
    → карточка с подтверждением до записи
иначе:
    → request_clarification (тексты §9.4), не пишем
```

### 9.3 Разделённый confidence
LLM возвращает не одно число, а три:
- `text_confidence` — уверен ли в распознанном Whisper тексте.
- `amount_confidence` — уверен ли в сумме (двадцать/двести путаются).
- `quantity_confidence` — уверен ли в количестве товара.

`critical_confidence = min(text, amount, quantity)` — категория и контрагент в формулу не идут (их можно поправить руками без последствий для остатков).

### 9.4 Тексты уточнений
| Случай | Текст бота |
|--------|-----------|
| Не понял команду | «Не понял операцию. Это продажа, закупка, расход или что-то ещё?» |
| Нет суммы для денежной операции | «На какую сумму?» |
| Нет товара для продажи/закупки | «Какой товар?» |
| Нет количества для движения товара | «Сколько штук/мешков/листов?» |
| Whisper мусор/тишина | «Я не разобрал. Попробуй ещё раз — говори ближе к микрофону.» |
| Голосовое > 60 сек | «Слишком длинное сообщение. Разбей на короткие — одна операция за раз.» |
| Чат не привязан | «Сначала привяжи Google-таблицу: `/link <ID>` и расшарь на сервисный аккаунт: `<email>`.» |
| Не в whitelist | «У вас нет доступа.» (или молчание при `SILENT_REJECT=true`) |
| После escape | «Диалог сброшен. Что записать?» |

### 9.5 Форматы подтверждений
**Продажа (S1, S2):**
```
Записал продажу: ГКЛ — 10 листов за 5 000 ₽ (наличные). Точка: магазин на Ленина. Остаток ГКЛ: 47.
```

**Закупка (S3):**
```
Записал закупку: штукатурка — 100 мешков за 25 000 ₽ (счёт). Поставщик: Петрович. Поступление на склад. Остаток штукатурки: 187.
```

**Возврат от покупателя (S4):**
```
Записал возврат: ГКЛ — 2 листа, вернул 1 000 ₽ (наличные). Остаток ГКЛ: 49.
```

**Возврат поставщику (S5):**
```
Записал возврат поставщику Петрович: штукатурка — 10 мешков, получено 2 500 ₽ (счёт). Остаток штукатурки: 177.
```

**Списание (S6):**
```
Списал: штукатурка — 3 мешка (бой). Остаток штукатурки: 174.
```

**Расход без товара (S7):**
```
Записал расход: 80 000 ₽ — аренда помещения (счёт).
```

**Перемещение (S9):**
```
Перевёз ГКЛ — 20 листов: со склада → магазин на Ленина. Остатки ГКЛ: склад 27, Ленина 35.
```

**Multi-ops (S12):**
```
Записал 2 продажи: цемент — 30 мешков за 18 000 ₽; ГКЛ — 10 листов за 5 000 ₽. Итого +23 000 ₽ (наличные).
```

### 9.6 Stateful-диалоги
SQLite таблица `dialog_state`:
- `chat_id` — ключ.
- `intent` — `clarify_money` / `clarify_goods` / `period_report` / `confirm_undo` / `canonicalize_product` / `canonicalize_location` / `dedup_check` / `inventory_step` / `edit_last`.
- `awaiting_field` — что ждём.
- `partial_data_json` — собранное.
- `expires_at` — TTL 5 минут.

`/cancel` или «отмена / забей / начни сначала» сбрасывает диалог. По таймауту — автосброс с сообщением.

## 10. Лист «Движение денег» — правила

### 10.1 Колонки
См. [data-model.md §1.1](./data-model.md). 10 колонок строго:
Дата, Время, Тип операции, Сумма (₽), Категория, Контрагент, Точка / Склад, Способ оплаты, Описание, tx_id.

### 10.2 Типы операций (значения колонки «Тип операции»)
| Значение | Когда |
|----------|-------|
| продажа | приход денег от покупателя за товар (связан tx_id с записью в «Товары») |
| закупка | расход денег поставщику за товар (связан tx_id) |
| расход | расход без товара (аренда, зарплата, коммуналка) |
| прочий приход | приход не от продажи (внесение в кассу, прочее) |
| возврат покупателю | расход денег при возврате товара (связан tx_id) |
| возврат поставщика | приход денег при возврате поставщику (связан tx_id) |
| внесение | пополнение кассы из личных |
| изъятие | снятие из кассы на личные |

### 10.3 Категории (только для «расход»)
**Дефолтный список (9 категорий), редактируемый через лист «Категории»:**
1. закупка товара — автоматически для типа «закупка»
2. аренда помещения
3. зарплата
4. коммунальные / связь
5. реклама / маркетинг
6. транспорт / доставка
7. налоги / банк / эквайринг
8. оборудование / ремонт
9. прочее

Для типов «продажа», «прочий приход», «возврат покупателю», «возврат поставщика», «внесение», «изъятие» — категория автоматически совпадает с типом (для удобства фильтрации).

### 10.4 Сумма
Целое число в рублях, без копеек. Парсинг числительных — см. [llm-parsing.md](./llm-parsing.md).

### 10.5 Контрагент
- Продажа: чаще пусто (`не указано`), для оптовых — имя бригады/клиента.
- Закупка: всегда поставщик (Леруа, Петрович...).
- Расход: получатель (Сбер, Алексей-электрик, аренодатель).

### 10.6 Точка / Склад
Канон из листа «Точки» / `не указано`. Дефолт `DEFAULT_LOCATION` из env, если не упомянуто.

### 10.7 Способ оплаты
`наличные` / `карта` / `счёт` / `не указано`.

### 10.8 Описание
Дословный фрагмент о сути, без вводных. Для связанных операций (продажа/закупка/возвраты) — список товаров через запятую («ГКЛ 10 л, цемент 5 мш»).

### 10.9 tx_id
Служебная колонка. Для одиночных операций (расход, внесение, изъятие) — пусто. Для связанных с движением товаров — UUID, общий с соответствующей строкой в «Движение товаров».

## 11. Лист «Движение товаров» — правила

### 11.1 Колонки
См. [data-model.md §1.2](./data-model.md). 11 колонок строго:
Дата, Время, Тип операции, Точка / Склад, Точка-источник, Контрагент, Товар, Количество, Единица измерения, Цена за ед. (₽), Комментарий, tx_id.

### 11.2 Типы операций
| Значение | Изменение остатков |
|----------|---------------------|
| поступление | +Q на (Точка/Склад). Связь с записью «закупка» в Деньгах через tx_id. |
| продажа | −Q с (Точка/Склад). Связь с «продажа» в Деньгах. |
| списание | −Q. Деньги не трогаются. |
| возврат покупателя | +Q (товар вернулся к нам). Связь с «возврат покупателю» в Деньгах. |
| возврат поставщику | −Q (товар ушёл от нас). Связь с «возврат поставщика» в Деньгах. |
| перемещение | две строки: −Q (Точка-источник), +Q (Точка/Склад). Деньги не трогаются. |
| инвентаризация | корректировка: −Q или +Q до фактического, категория «инвентаризация», деньги не трогаются. |

### 11.3 Точка-источник
Заполняется только для **перемещений** (откуда). Для всех остальных типов — пусто.

### 11.4 Товар
Канон из листа «Товары». Незнакомый → канонизация (§7).

### 11.5 Количество
Число, может быть дробным («полтора куба»). Для списания и продажи — положительное; знак минуса не пишем, тип операции сам подразумевает выбытие.

### 11.6 Единица измерения
Канонизированная из словаря (см. [data-model.md §1.4](./data-model.md)).

### 11.7 Цена за единицу
Опциональная колонка. Заполняется при **поступлении** (расчёт: сумма закупки / количество) — нужно для средневзвешенной цены закупки в Остатках. Для продажи можно заполнять или нет (если есть — попадает в маржинальные расчёты v2).

### 11.8 tx_id
Связывает с парной записью в «Движение денег» (для продажи/закупки/возвратов). Для списания, перемещения, инвентаризации — пусто или UUID без пары.

## 12. Лист «Остатки» — правила

### 12.1 Это **расчётный** лист, обновляется ботом
Колонки: Товар, Единица, Точка / Склад, Количество, Средневзвешенная цена закупки (₽), Обновлено.

### 12.2 Когда пересчитывается
После каждой записи в «Движение товаров»: бот обновляет строку `(Товар, Точка/Склад)`:
- **+Q** (поступление, возврат покупателя, перемещение в): количество растёт, СВ-цена пересчитывается.
- **−Q** (продажа, списание, возврат поставщику, перемещение из): количество уменьшается, СВ-цена не меняется.
- **Корректировка инвентаризации**: количество ставится в фактическое, в Лог фиксируется разница.

### 12.3 Формула СВ-цены закупки
```
новая_СВ_цена = (старое_кол × старая_СВ_цена + Q_поступления × цена_поступления) / (старое_кол + Q_поступления)
```
Если `цена_поступления` пуста — СВ не меняется.

### 12.4 Защита
- Бот **не разрешает** пользователю править лист «Остатки» руками. Если детектирует ручную правку — предупреждение «Лист «Остатки» обновляется только ботом. Чтобы скорректировать — сделай `/inventory`».
- Защита через проверку хэша всех строк перед каждой записью; при расхождении — `/repair stock` пересобирает Остатки полностью из «Движение товаров».

### 12.5 Команда `/stock`
- `/stock` — все товары, итог по всем точкам.
- `/stock ГКЛ` — конкретный товар, разбивка по точкам.
- `/stock ГКЛ Ленина` — товар на конкретной точке.
- Голосом: «Сколько ГКЛ на складе?» — то же что `/stock ГКЛ Склад`.

## 13. Отчёты

### 13.1 `/today` — промежуточный
```
На сейчас (15:42, 31.05.2026):
– Продажи: 47 000 ₽ (8 операций)
– Закупки: 12 800 ₽ (1 операция, Петрович)
– Прочие расходы: 5 000 ₽ (1 операция)
– Возвраты: −2 000 ₽
– Чистый итог: +27 200 ₽
```

### 13.2 Ежедневный автоотчёт (21:00)
Расширенный по сравнению с прорабским ТЗ:
```
Финансы за сегодня:
– Продажи: 87 000 ₽ (15 операций)
– Закупки: 35 200 ₽ (2)
– Прочие расходы: 8 500 ₽ (3)
– Возвраты: −2 000 ₽
– Итог по кассе: +41 300 ₽

Топ-3 товара по выручке:
1. ГКЛ — 18 000 ₽ (20 листов)
2. цемент — 14 400 ₽ (24 мешка)
3. штукатурка — 12 600 ₽ (18 мешков)

Точки:
– магазин на Ленина: 52 000 ₽
– магазин на Зорге: 35 000 ₽
```

**SLA:** при ошибке отправки — ретрай каждые 60 сек, до 5 попыток. После — запись в SQLite, на следующий день — накопительный отчёт с пометкой «за вчера + за сегодня».

### 13.3 Сводный отчёт за период
Триггер: голос «отчёт за месяц/квартал/год» или `/report`.

**Парсинг периода:** правило дефолтного года — текущий, если в будущем → прошлый.

**Уточнение** при неоднозначности — «За какой период: текущий или конкретный?».

**Формат:**
```
Финансовый отчёт за май 2026:
– Продажи: 1 245 000 ₽ (218 операций)
– Закупки: 720 000 ₽ (18)
– Прочие расходы: 165 000 ₽
   • аренда: 80 000 ₽
   • зарплата: 60 000 ₽
   • коммунальные: 12 000 ₽
   • прочее: 13 000 ₽
– Возвраты покупателям: 18 000 ₽
– Возвраты поставщикам: 5 000 ₽
– Итог: +347 000 ₽

Топ-3 товара по выручке:
1. цемент — 215 000 ₽ (358 мешков)
2. ГКЛ — 180 000 ₽ (240 листов)
3. штукатурка — 142 000 ₽ (228 мешков)

Точки:
1. магазин на Ленина — 720 000 ₽ выручки, 195 000 ₽ прибыль
2. магазин на Зорге — 525 000 ₽ выручки, 152 000 ₽ прибыль
```

### 13.4 Метрики топа (голосовая команда меняет)
- «отчёт за месяц **по выручке**» — топ-товаров по обороту продаж (дефолт).
- «**по прибыли**» — выручка минус закупочная стоимость по товару.
- «**по количеству**» — топ по штукам/мешкам.
- «**по точкам**» — разбивка по точкам, всегда добавляется в конец.

### 13.5 Отчёт по остаткам
`/stock` или голос «остатки», «что на складе» → возврат таблицы остатков с группировкой по точкам.

## 14. Архитектура

### 14.1 Источник правды
**Sheets — единственный источник правды по учётным данным.** SQLite — только техническое состояние, не дублирует операции.

### 14.2 Компоненты
| Модуль | Назначение |
|--------|------------|
| `src/bot/` | MAX-клиент (long-polling в MVP), роутер, обработчики команд |
| `src/stt/` | Whisper API, `language="ru"`, опц. noisereduce |
| `src/llm/` | Claude tool_use: текст → ParsedCommand |
| `src/sheets/` | gspread: чтение/запись 6 листов, инициализация структуры, защита Остатков, обработка ручных правок |
| `src/stock/` | Пересчёт остатков, СВ-цена, защита от ручных правок, `/repair stock` |
| `src/domain/` | Pydantic: Sale, Purchase, Return*, Writeoff, Movement, CashFlow, Inventory, StockItem, Confidence, ParsedCommand |
| `src/reports/` | Сводные отчёты из Sheets, форматирование |
| `src/scheduler/` | Дневной автоотчёт + ретраи |
| `src/storage/` | SQLite: idempotency, dedup_window, dialog_state, operations_log, pending_writes, products_cache, locations_cache |
| `src/dialog/` | Stateful-диалоги: уточнения, канонизация (товаров и точек), dedup, undo, inventory |
| `src/config/` | env, whitelist, пороги |

### 14.3 Поток данных
```
MAX (voice) ──► STT (Whisper) ──► LLM (Claude tool_use) ──► решение по UX (§9.2)
                                                                │
                                  ┌─────────────────────────────┼─────────────────────────────┐
                                  ▼                             ▼                             ▼
                            запись сразу                   карточка                     clarification
                                  │                             │                             │
                                  ▼                             ▼                             ▼
                            транзакция:               ждём ✅/✏️/❌                  диалог в SQLite
                            • Движение денег
                            • Движение товаров
                            • Остатки (пересчёт)
                            одним tx_id
                                  │
                                  ▼
                            подтверждение в MAX
                                  │
                                  ▼
                            SQLite operations_log
                            (для /undo и audit)
```

### 14.4 Транзакционность
Sheets API не транзакционен. Чтобы избежать «полузаписей» (деньги записаны, товары нет, остатки разъехались) — двухфазный паттерн:

1. **Подготовка:** все строки для записи готовятся в памяти (Деньги, Товары, обновления Остатков), валидируются.
2. **Запись 1 — Движение товаров.** Если упало — fail, ничего не записано, retry или pending_writes.
3. **Запись 2 — Движение денег.** Если упало — компенсация: удалить только что записанные товары + retry.
4. **Запись 3 — Остатки.** Если упало — пересчёт остатков фоном из «Движение товаров» (не критично, остатки расчётные).
5. **Логирование в SQLite operations_log** с `tx_id`, sheet rows, статусом.

При `/undo` бот находит все строки по `tx_id` и удаляет их одной серией, потом пересчитывает Остатки.

### 14.5 MAX Bot API
- MVP: long-polling, без публичного HTTPS.
- v2: webhook.
- На момент 2026-05 готовая Python-обёртка может отсутствовать — план B тонкий httpx-клиент.

### 14.6 STT, LLM, Deploy
- STT: Whisper API (`whisper-1`), русский. Митигация шума на стройке/в магазине — карточка для крупных сумм, разделённый confidence, опц. noisereduce.
- LLM: Claude Haiku 4.5 основной, Sonnet 4.6 fallback при `critical_confidence < 0.7`.
- Deploy: VPS 1 vCPU / 1 GB RAM, systemd, бэкап Sheets в `.xlsx` еженедельно.

## 15. Нефункциональные требования

### 15.1 Производительность
Целевое «голос отправлен → подтверждение в чате»: **< 10 сек** (на 2 секунды больше прорабской из-за пересчёта остатков и канонизации). Декомпозиция: Whisper 2–4с, Claude 1–2с, Sheets 3 записи + пересчёт 2–3с.

### 15.2 Лимиты
- Голосовое ≤ 60 сек (мягкий).
- Whisper ≤ 25 МБ (hard).
- Sheets API: 60 req/min/user. Узкое место — пересчёт остатков; батчим обновления.

### 15.3 Безопасность
- Whitelist `ALLOWED_USER_IDS`. Опц. `SILENT_REJECT`.
- PIN `OPS_PIN` обязателен для `/undo`, `/edit last`, `/inventory`.
- Никаких секретов в коде/коммитах.
- Sheets расшарена только на email service account.
- Лист «Остатки» защищён от ручных правок (см. §12.4).

### 15.4 Надёжность
- Падение Whisper / Claude / Sheets → понятное сообщение, не молчит.
- Очередь `pending_writes` при недоступности Sheets, ретрай каждые 60 сек.
- Идемпотентность: `message_id` + семантический хэш.
- При падении бота systemd рестарт, SQLite сохраняет всё.

### 15.5 Деньги и точность
- Внутри домена суммы — копейки `int`.
- В Sheets — целые рубли.
- Количество товара — `float` (для дробных единиц).

### 15.6 Бюджет API
Оценка для активного магазина (~80 операций/день):
- Whisper: ~$2.4/мес
- Claude Haiku: ~$15/мес
- Sonnet fallback (~20%): ~$5/мес
- VPS: ~$5/мес
**Итого: ~$28/мес.** Опц. `MONTHLY_API_BUDGET_USD` — при превышении бот приостанавливает запись и предупреждает.

## 16. AI-парсинг

Полное описание — [llm-parsing.md](./llm-parsing.md). Кратко:

### 16.1 Инструменты Claude (tool_use), 14 шт.
1. `record_sale` — продажа товара.
2. `record_purchase` — закупка товара.
3. `record_return_from_customer` — возврат от покупателя.
4. `record_return_to_supplier` — возврат поставщику.
5. `record_cashflow` — приход/расход без товара (аренда, зарплата, внесение, изъятие).
6. `record_writeoff` — списание товара.
7. `record_movement` — перемещение между складами.
8. `record_inventory_adjustment` — корректировка остатков по факту.
9. `query_stock` — запрос остатков.
10. `resolve_report_period` — парсинг периода для отчёта.
11. `canonicalize_product` — выбор канон-имени товара или создание нового.
12. `canonicalize_location` — то же для точки/склада.
13. `apply_edit` — правка последней операции.
14. `request_clarification` — нет обязательных полей или непонятно.

### 16.2 Required-поля
Все обязательные явно помечены `required` в JSON-schema. Опциональные — `nullable: true`.

### 16.3 Системный промпт
Семантика, не словари. Разделённый confidence (text / amount / quantity). Правило дефолта года.

## 20. Глоссарий

| Термин | Значение |
|--------|----------|
| Точка | Торговая точка или склад магазина (магазин на Ленина, склад на Зорге) |
| Канон товара / точки | Каноническое имя в справочнике; альтернативные произношения — алиасы |
| Транзакция | Атомарная операция, затрагивающая Деньги + Товары + Остатки одновременно, связана общим `tx_id` |
| Остатки | Расчётный лист с текущим количеством каждого товара по каждой точке. Обновляется ботом, владелец не правит |
| СВ-цена | Средневзвешенная цена закупки товара; пересчитывается при каждом поступлении |
| Карточка | Сообщение бота с распарсенной операцией и кнопками подтверждения до записи |
| Канонизация | Процесс отображения произнесённого имени (товара/точки) на канон в справочнике |
| Дедуп | Семантическая дедупликация: повтор операции в окне 5 мин |
| Multi-ops | Несколько отдельных операций в одной голосовой фразе |
| Двухфазная запись | Паттерн транзакционной записи в Sheets с компенсацией при частичном сбое |
| pending_write | Состояние операции в SQLite, ждущей успешной записи в Sheets |

## 21. Эволюция структуры Sheets

### 21.1 Что может клиент

**Может (безопасно):**
- Добавлять любые колонки **справа** от ботовских во всех листах. Бот их не трогает.
- Добавлять формулы, условное форматирование, фильтры, цвета — это всё в Sheets.
- Расширять список категорий через лист «Категории» (см. §10.3).
- Завершать товары/точки (выставлять `Статус = архив` вручную в справочниках).
- Добавлять новые листы в книгу для своих нужд.

**Не может (бот не даст):**
- Переименовывать ботовские колонки.
- Удалять ботовские колонки.
- Менять порядок ботовских колонок.
- Править лист «Остатки» руками (§12.4).

### 21.2 Что делает бот, если структура сломана
При каждом запуске и перед каждой записью бот проверяет заголовки обязательных листов. Если расхождение:
1. **Лог в SQLite** с указанием, какая колонка пропала.
2. **Стоп записи** для этого листа — `pending_writes` копятся.
3. **Сообщение владельцу:** «Не нашёл колонку «Сумма (₽)» в листе «Движение денег». Восстанови — или жми `/repair sheets` чтобы я пересоздал структуру (старые данные сохраню в архивном листе).»

### 21.3 Как добавить новую системную колонку (фича)
Это **не самостоятельное действие клиента**, а доработка бота:
1. Клиент пишет/говорит «хочу колонку «Маржа» в продажах».
2. Мы оцениваем сложность (1–4 часа обычно).
3. Обновляем в коде: схему листа, маппинг tool_use → строка, формат подтверждения.
4. Деплоим. При следующей записи бот сам создаёт колонку и начинает заполнять.

### 21.4 Стратегия миграций
- **Версия схемы хранится в служебной ячейке `A1` каждого обязательного листа** как комментарий: `«max-money-bot v1.0»`. При обновлении бота:
  - Если версия совпадает — работаем.
  - Если ниже — миграция: добавление новых колонок справа от ботовских (но левее клиентских!), переименований не делаем.
  - Если выше — отказ: «нужно обновить бот».
- **Архивирование:** при `/repair sheets` старая структура копируется в `Архив_<дата>`, новая создаётся чисто. Данные не теряются.

### 21.5 Multi-tenant специфика (для v2)
Сейчас single-tenant, каждый клиент = свой инстанс бота. Если у разных клиентов разные колонки/категории — в коде используется один контракт (этот SPEC). Для частичных кастомизаций конкретного клиента — overrides в `tenant_config.yaml` в коде клиента, не в Sheets. Это позволяет:
- Включать/выключать опциональные листы.
- Менять дефолтный список категорий и единиц измерения.
- Добавлять кастомные tool_use инструменты (для специфики клиента).

Клиент при этом ничего настраивать не должен — он получает работающий бот с уже подходящей для него конфигурацией.
